# 分诊

把项目问题跟踪器上的 issue 推过一个由分诊角色组成的小状态机。

如果这个仓库把外部 PR 当作请求入口（见 issue 跟踪器配置），分诊也覆盖它们：**PR 就是带着代码的 issue**——同样的角色、同样的状态、同样的状态机，外加下面几处标着"PR 专用"的差异。裸露的 `#42` 按跟踪器配置解析为 issue 或 PR。

分诊期间发到问题跟踪器的每条评论或 issue **必须**以这个免责声明开头：

```
> *这是 AI 在分诊期间生成的。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何撰写耐用的 Agent 简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库如何运作

## 角色

两个**类别**角色：

- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

五个**状态**角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等报告者补充信息
- `ready-for-agent` — 完全指定，AFK Agent 可接手
- `ready-for-human` — 需要人类实现
- `wontfix` — 不予处理

对 PR 来说，同样的状态对着附加的代码读：`ready-for-agent` 表示已附简报、Agent 应该对 diff 采取下一步；`ready-for-human` 表示已就绪、等人类合并。

每个分诊过的 issue 应该恰好带一个类别角色和一个状态角色。如果状态角色冲突，标记出来，在做任何别的事之前先问维护者。

这些是规范角色名——问题跟踪器里实际使用的标签字符串可能不同。映射应该已经提供给你。如果没有，告诉用户先运行 `setup-matt-pocock-skills`。

状态转移：无标签的 issue 通常先进 `needs-triage`；从那里再移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。`needs-info` 在报告者回复后回到 `needs-triage`。维护者任何时候都可以覆盖——把不寻常的转移标记出来，问过再继续。

## 调用方式

维护者调用 `triage` 并用自然语言描述想要什么。解读请求并执行。示例：

- "给我看看所有需要我注意的东西"
- "我们看看 #42"（issue 或 PR）
- "把 #42 移到 ready-for-agent"
- "有什么是 Agent 可以接手的？"

## 展示需要注意的东西

查询问题跟踪器，按最旧优先呈现三桶：

1. **无标签** — 从没分诊过。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且报告者在上次分诊笔记之后有活动** — 需要重新评估。

当 PR 在范围内时，把外部 PR 也放进这些桶，每行标 `[PR]` 或 `[issue]`。发现只浮出*外部* PR（跟踪器配置定义谁算外部）——协作者进行中的 PR 不是分诊工作。这个过滤只用于发现；被明确点名的 PR 无论作者是谁都要分诊。

显示数量，每项一行摘要。让维护者挑。

## 分诊一个具体的 issue 或 PR

1. **收集上下文。** 读完整的 issue 或 PR（正文、评论、标签、作者、日期；PR 还要读 diff）。解析以前的分诊笔记，别重复问已经解决的问题。用项目的领域术语表探索代码库，尊重该区域的 ADR。对代码库跑两项检查：(a) **冗余** — 按领域概念搜索请求行为是否已有实现（不是只按请求的原话搜），并报告你找过哪些地方。找到了，就是"已实现"的 `wontfix`（步骤 5）。(b) **曾被拒绝** — 读 `.out-of-scope/*.md`，浮出任何相似的历史请求。

2. **建议。** 告诉维护者你的类别和状态建议及理由，外加一段与请求相关的代码库摘要——包括它是否已经实现。等待指示。

3. **验证主张。** 任何盘问之前，先验证主张是否成立。对 bug，按报告者的步骤复现。对 PR，确认 diff 做到了它声称的事——check out 出来，跑相关测试或命令。报告结果：确认（含代码路径）、失败、或细节不足（强烈的 `needs-info` 信号）。验证确认过的主张能做出强得多的 Agent 简报。

4. **盘问（如果需要）。** 如果请求需要充实，调用 Skill 工具两次，分别是 "grilling" 和 "domain-modeling"——一轮一轮地问，把它盘成型，领域术语随敲定即时更新 `CONTEXT.md`/ADR。

5. **应用结果：**
   - `ready-for-agent` — 发一条 Agent 简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 结构和 Agent 简报一样，但要注明为什么不能委托（判断性决策、外部访问、设计决定、手动测试）。
   - `needs-info` — 发分诊笔记（下面的模板）。
   - `wontfix` — 关闭，评论取决于*为什么*：
     - **已经实现** — 改动已存在于代码库。指出它住在哪；**不要**写 `.out-of-scope/`（那个知识库记的是*被拒绝*的请求，不是已实现的）。
     - **拒绝（bug）** — 礼貌解释，然后关闭。
     - **拒绝（enhancement）** — 写入 `.out-of-scope/`，从评论里链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 应用角色。有部分进展时可加可选评论。

## 快速状态覆盖

如果维护者说"把 #42 移到 ready-for-agent"，相信他们，直接应用角色。确认你即将做的事（角色变更、评论、关闭），然后执行。跳过盘问。如果在没有盘问会话的情况下移到 `ready-for-agent`，问一句要不要写 Agent 简报。

## needs-info 模板

```markdown
## 分诊笔记

**目前已确认：**

- 要点 1
- 要点 2

**还需要你（@报告者）补充：**

- 问题 1
- 问题 2
```

盘问期间敲定的所有东西都记到"目前已确认"下面，别让工作白费。问题必须具体可执行，而不是"请提供更多信息"。

## 恢复上一次会话

如果 issue 或 PR 上已有分诊笔记，先读它们，检查报告者是否回答了任何未决问题，在继续之前呈现更新的图景。别重复问已解决的问题。
