# 改善代码库架构

把架构摩擦浮出水面，提出**深化机会**——把浅模块变成深模块的重构。目标是可测试性和 AI 可导航性。

这一命令由项目的领域模型提供*信息*，并建立在一套共享的设计词汇上：

- 用技能名 "codebase-design" 调用 Skill 工具获取架构词汇（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原则（删除测试、"接口就是测试面"、"一个适配器 = 假设接缝，两个 = 真实接缝"）。每条建议都严格使用这些术语——不要漂移到"组件""服务""API"或"边界"。
- `CONTEXT.md` 里的领域语言为好接缝命名；`docs/adr/` 里的 ADR 记录了这一命令不该重新提起的决策。

## 流程

### 1. 探索

**先定范围再扫描——YAGNI。** 深化一个模块的回报在于让未来对它做修改更轻松，所以要多加权那些最近刚改过的部分。先决定*看哪里*，再去看：

- 用户指名了方向——一个模块、一个子系统、一个痛点——就照办，跳过下面的推断。
- 否则，往回走一段可观的提交历史（`git log --oneline`），找出代码库的热点——反复出现的文件和区域——让这些路径先抓住你的注意力。如果改动分散、没有明显热点，就放宽范围。

先读项目的领域术语表（`CONTEXT.md`）和你所接触区域的任何 ADR。

然后派一个子代理走查代码库。不要套死板的启发式——有机地探索，记下你在哪里体验到摩擦：

- 哪里理解一个概念需要在许多小模块之间来回跳？
- 哪些模块是**浅**的——接口几乎和实现一样复杂？
- 哪里纯函数只是为了可测试性而抽出，但真正的 bug 藏在它们*如何被调用*里（没有**局部性**）？
- 哪些紧耦合模块跨过自己的接缝泄漏了？
- 代码库的哪些部分没测试，或者很难通过现有接口测试？

对任何你怀疑"浅"的东西应用**删除测试**：删掉它会让复杂性集中，还是只是挪个地方？"会集中"正是你要的信号。

### 2. 把候选呈现为 HTML 报告

写一个自包含的 HTML 文件到操作系统临时目录，别让任何东西落进仓库。从 `$TMPDIR` 解析临时目录，回退到 `/tmp`（Windows 上是 `%TEMP%`），写到 `<tmpdir>/architecture-review-<timestamp>.html`，让每次运行都得到新文件。为用户打开它——Linux 用 `xdg-open <path>`，macOS 用 `open <path>`，Windows 用 `start <path>`——并告诉他们绝对路径。

报告用**CDN 的 Tailwind**做布局样式，图形/流程/时序能可靠传达结构的地方用**CDN 的 Mermaid**画图。把 Mermaid 和手绘 CSS/SVG 视觉混合使用——关系是图状的（调用图、依赖、时序）用 Mermaid，想要更编辑化表达的（体量图、剖面、折叠动画）用手工 div/SVG。每个候选配一个**改前/改后可视化**。要视觉化。

每个候选渲染一张卡片，包含：

- **文件** — 涉及哪些文件/模块
- **问题** — 为什么当前架构造成摩擦
- **方案** — 会发生什么改变的平实描述
- **收益** — 用局部性和杠杆来解释，以及测试会如何改善
- **改前 / 改后图解** — 并排、手绘，展示浅度与深化
- **推荐强度** — `Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章

报告结尾加一个**首推**小节：你会先啃哪个候选、为什么。

**领域用 `CONTEXT.md` 词汇，架构用 `codebase-design` 词汇。** 如果 `CONTEXT.md` 定义了 "Order"，就说"订单接收模块"——不是"那个 FooBarHandler"，也不是"订单服务"。

**ADR 冲突**：如果某候选与既有 ADR 矛盾，只有当摩擦真实到值得重开 ADR 时才浮出它。在卡片上清楚标记（例如一个警告标注：_"与 ADR-0007 矛盾——但值得重开，因为……"_）。不要列举 ADR 禁止的所有理论重构。

完整 HTML 脚手架、图解模式和样式指南见 [HTML-REPORT.md](HTML-REPORT.md)。

此刻**不要**提议接口。文件写完后问用户："你想探索哪一个？"

### 3. 盘问循环

用户选定候选后，用技能名 "grilling" 调用 Skill 工具，和他们走决策树——约束、依赖、深化后模块的形状、接缝后面放什么、哪些测试能活下来。

决策成形时副作用就地发生——随时用 "domain-modeling" 调用 Skill 工具，保持领域模型不过时：

- **给深化后的模块起了一个 `CONTEXT.md` 里没有的概念名？** 把这个术语加进 `CONTEXT.md`。文件不存在就按需创建。
- **对话中锐化了一个模糊术语？** 就地更新 `CONTEXT.md`。
- **用户用一个承重的理由拒绝了候选？** 提议一条 ADR，措辞如：_"要我把它记成 ADR 吗？这样未来的架构审查就不会再提同样的建议。"_ 只有当这个理由确实是未来探索者需要用来避免重提时才算——短暂的理由（"现在不值得做"）和自明的理由跳过。
- **想为深化后的模块探索替代接口？** 用技能名 "codebase-design" 调用 Skill 工具，用它那套"设计两次"的并行子代理模式。
