# 领域建模

在设计过程中主动构建并打磨项目的领域模型。这是一门"主动出击"的学科——质疑术语、构造边界场景，并在术语和决策成形的当下把它们写下来。（仅仅是*阅读* `CONTEXT.md` 里的词汇并不算本技能——那是任何技能都能做到的一行好习惯。本技能用于你**改变**模型的时刻，而不是消费模型的时候。）

## 文件结构

大多数仓库只有一个上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，说明这个仓库有多个上下文。映射文件指明每个上下文住在哪里：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 该上下文的决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需创建文件——只有当你有内容可写时才建。如果 `CONTEXT.md` 不存在，就在第一项术语敲定之后创建它。如果 `docs/adr/` 不存在，就在需要第一条 ADR 时创建它。

## 会话期间

### 质疑词汇

当用户使用的术语与 `CONTEXT.md` 中已有的语言冲突时，立即指出。"你的词汇表把 'cancel' 定义为 X，但你刚才的意思似乎是 Y——到底是哪个？"

### 锐化模糊表达

当用户用词模糊或宽泛时，提出一个精确的规范术语。"你说的'账户'——指客户还是用户？它们是不同的东西。"

### 用具体场景施压

讨论领域关系时，用具体场景做压力测试。构造一些场景去探测边界情况，逼着用户把概念之间的界线说确切。

### 与代码交叉核对

当用户描述某件事如何运作时，检查代码是否一致。发现矛盾就指出来："你的代码把整个订单都取消了，但你刚说可以部分取消——这是对的吗？"

### 就地更新 CONTEXT.md

某条术语一经敲定，立即更新 `CONTEXT.md`。不要攒批处理——定一条记一条。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应该完全不包含实现细节。不要把它当成规格说明、草稿本或实现决策的存放处。它只是术语表，仅此而已。

### 谨慎地提出 ADR

只有以下三个条件全部满足时，才提议创建 ADR：

1. **难以逆转**——日后改弦更张的成本不可忽视
2. **缺乏上下文会令人意外**——未来的读者会纳闷"他们当初为什么这么做？"
3. **真的是权衡得出的结果**——确实存在若干备选方案，而你出于具体理由选择了其中一个

三者缺一，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
