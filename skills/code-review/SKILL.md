对 `HEAD` 与用户提供的固定点之间的差异做双轴审查：

- **标准轴** — 代码是否符合本仓库文档化的编码标准？
- **规格轴** — 代码是否忠实实现了最初的问题/规格？

两条轴都作为**并行子代理**运行，避免互相污染上下文，本技能随后汇总它们的发现。

问题跟踪器应该已经提供给你。如果缺少 `docs/agents/issue-tracker.md`，告诉用户先运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 确定固定点

用户说的任何东西都可能是固定点——提交 SHA、分支名、标签、`main`、`HEAD~5` 等。若用户没指定，主动询问。

一次性记录 diff 命令：`git diff <fixed-point>...HEAD`（三个点，比较的是合并基线）。另外通过 `git log <fixed-point>..HEAD --oneline` 记录提交列表。

继续之前，确认固定点能解析（`git rev-parse <fixed-point>`）且 diff 非空。引用无效或 diff 为空，应该在这里就失败——而不是在两个并行子代理内部失败。

### 2. 确定规格来源

按以下顺序寻找最初的规格：

1. 提交消息里对 issue 的引用（`#123`、`Closes #45`、GitLab `!67` 等）——按 `docs/agents/issue-tracker.md` 中的工作流抓取。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名或功能匹配的规格文件。
4. 什么都没找到就问用户规格在哪里。若用户说没有，**规格轴**子代理应跳过并报告"无可用规格"。

### 3. 确定标准来源

仓库中任何说明代码该怎么写的文档，例如 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`。

除了仓库自己的文档，标准轴始终带着下面的**坏味道基线**——一组固定的 Fowler 代码坏味道（《重构》第 3 章），即使仓库什么都没写也照样适用。两条规则约束它：

- **仓库优先。** 文档化的仓库标准永远胜出；基线本来会标记、而仓库标准认可的东西，不报坏味道。
- **永远是判断。** 每种坏味道都是带标签的启发式（"疑似依恋情节"），绝不是硬性违规——而且与这里任何标准一样，工具已经在强制检查的东西就跳过。

每种坏味道读作*它是什么* → *怎么修*；与 diff 对照：

- **神秘命名** — 函数、变量或类型的名字看不出它做什么、持有什么。→ 重命名；想不出诚实的名字，说明设计本身混沌。
- **重复代码** — 同样的逻辑形状在改动的多个 hunk 或文件中反复出现。→ 提取共享逻辑，两处都调用它。
- **依恋情节（Feature Envy）** — 方法访问别的对象的数据多过访问自己的。→ 把方法移到它所依恋的数据上。
- **数据泥团** — 同样的几个字段或参数总是结伴出现（一个想出生的类型）。→ 打包成一个类型传出去。
- **基本类型偏执** — 用基本类型或字符串顶替本该拥有自己类型的领域概念。→ 给这个概念造一个小类型。
- **重复的分支** — 同一类型上相同的 `switch`/`if` 级联在改动中反复出现。→ 用多态替换，或让多处共用一张表。
- **散弹式修改** — 一个逻辑改动逼着你在 diff 的许多文件里到处小改。→ 把一起变的东西收进一个模块。
- **发散式变化** — 一个文件或模块因为好几个互不相干的原因被改。→ 拆分，让每个模块只为一个原因变化。
- **投机性通用性** — 为规格里并没有的需求添加抽象、参数或钩子。→ 删掉；内联回去，直到真实需求出现。
- **消息链** — 调用方不该依赖的长链式导航 `a.b().c().d()`。→ 把链路藏进第一个对象的某个方法后面。
- **中间人** — 某个类或函数大部分工作只是往里转发。→ 砍掉它，直接调用真正的目标。
- **拒绝继承的馈赠** — 子类或实现类忽略/覆盖了所继承的大部分内容。→ 放弃继承，改用组合。

### 4. 并行启动两个子代理

**标准轴子代理提示词** — 包括：

- 完整的 diff 命令和提交列表。
- 你在第 3 步找到的标准来源文件列表，**加上第 3 步的坏味道基线原文完整粘贴**——子代理没有渠道自行获取。
- 任务简报："按文件/hunk 汇报——(a) diff 里每一处违反文档化标准的地方：引用标准（文件 + 规则）；(b) 你发现的任何基线坏味道：报名字并引用对应 hunk。硬违规与判断性结论要区分开——违反文档化标准可以是硬违规，但基线坏味道永远是判断性结论，且仓库文档化的标准覆盖基线。工具已强制检查的跳过。400 字以内。"

**规格轴子代理提示词** — 包括：

- diff 命令和提交列表。
- 规格的路径或抓取到的内容。
- 任务简报："汇报：(a) 规格要求了但缺失或不全的需求；(b) diff 里规格没要求的行为（范围蔓延）；(c) 看起来已实现但实现方式可疑的需求。每条发现都引用规格原文。400 字以内。"

若规格缺失，跳过规格轴子代理，并在最终报告里注明。

### 5. 汇总

在 `## 标准轴` 和 `## 规格轴` 两个标题下原样或轻度整理后呈现两份报告。**不要**合并或重排发现——两条轴是刻意分开的（见*为什么是两条轴*）。

结尾给一行总结：每条轴各有多少发现、以及*各轴内部*最严重的问题（如有）。不要跨轴评出一个总冠军——这正是分轴报告要避免的重排。

## 为什么是两条轴

一个改动可能过了一条轴、栽在另一条轴上：

- 代码每个标准都符合、但实现错了东西 → **标准轴过，规格轴挂。**
- 代码完全按 issue 要求做了、但破坏了项目惯例 → **规格轴过，标准轴挂。**

分开汇报就是防止一根轴掩盖另一根轴。
