# 诊断 Bug

一门针对疑难 bug 的纪律。只有明确有理由时才跳过阶段。

探索代码库时，读 `CONTEXT.md`（如果存在）以获得相关模块清晰的脑内模型，并检查你所接触区域的 ADR。

## 脱敏

这项技能会让你展示命令、输出和捕获的产物。**先脱敏所有机密**——用 `<REDACTED>` 占位。让循环依赖环境变量，让凭据留在环境里而不是你展示的内容里。捕获的产物带着认证头：只引用携带信号的那几行。

如果脱敏后的输出不足以诊断 bug，说出来并向用户要。

## 阶段 1 —— 建立反馈循环

**这就是本技能的全部。** 其余的都是机械操作。如果你对这个 bug 有一个**紧**的通过/失败信号——一条在*这个* bug 上会变红的信号——你就能找到原因；二分、假设检验、插桩都是在消费它。如果没有，盯着代码看多久都没用。

在这里投入不成比例的精力。**要激进。要有创意。拒绝放弃。**

### 构建方法 —— 大致按这个顺序尝试

1. **失败测试**，放在任何够得着 bug 的接缝处——单元、集成、端到端。
2. **Curl / HTTP 脚本**，对着运行中的开发服务器。
3. **CLI 调用**配夹具输入，把 stdout 与已知良好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM/console/network。
5. **重放捕获的踪迹。** 把真实的网络请求 / 载荷 / 事件日志存到磁盘；让代码路径在隔离状态下重放它。
6. **丢弃式测试台。** 拉起系统的最小子集（一个服务、模拟依赖），用一次函数调用就能触发 bug 代码路径。
7. **性质 / 模糊循环。** 如果 bug 是"偶尔输出错误"，跑 1000 个随机输入找失败模式。
8. **二分测试台。** 如果 bug 出现在两个已知状态之间（提交、数据集、版本），自动化"在状态 X 启动、检查、重复"，让 `git bisect run` 能跑起来。
9. **差分循环。** 把同一个输入跑过旧版 vs 新版（或两种配置），diff 输出。
10. **HITL bash 脚本。** 最后手段。如果必须有人来点，用 `scripts/hitl-loop.template.sh` 驱*动那个人*，让循环仍然有结构。捕获的输出会回流给你。

建对反馈循环，bug 就修好了 90%。

### 收紧循环

把循环当作产品。一旦你有了*一个*循环，**收紧**它：

- 能更快吗？（缓存初始化、跳过无关启动、缩小测试范围。）
- 能让信号更尖锐吗？（断言具体症状，而不是断言"没崩"。）
- 能更确定吗？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

一个 30 秒的抖动循环几乎等于没有循环；一个 2 秒的确定性循环是紧的——是调试的超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**。把触发器循环 100 次、并行化、加压力、收窄时间窗口、注入 sleep。一个 50% 抖动率的 bug 是可调试的；1% 不是——持续抬高复现率直到可调试为止。

### 当你真的建不出循环时

停下并明确说出来。列出你试过的东西。向用户要：(a) 能复现它的环境的访问权，(b) 一份脱敏的捕获产物（HAR 文件、日志转储、核心转储、带时间戳的录屏），或 (c) 加临时生产插桩的许可。没有循环，**不要**进入假设阶段。

### 完成标准 —— 一条会变红的紧循环

当循环是**紧**的且**能变红**时，阶段 1 完成：你能说出**一条命令**——一个脚本路径、一次测试调用、一个 curl——你**已经至少跑过一次**（展示调用和输出，脱敏后），并且它是：

- [ ] **能变红** — 它驱动真正的 bug 代码路径，并断言**用户的确切症状**，所以它能在这个 bug 上变红、修好后变绿。不是"运行不报错"——它必须能*抓住这个具体的 bug*。
- [ ] **确定性** — 每次运行同一结论（抖动 bug：固定的高复现率，见上）。
- [ ] **快** — 秒级，不是分钟级。
- [ ] **Agent 可运行** — 你能无人值守地跑它；人类只通过 `scripts/hitl-loop.template.sh` 参与。

如果这条命令还没出现你就开始读代码建理论，**停下来——直接跳进假设，正是本技能要防止的失败。** 没有能变红的命令，就没有阶段 2。

## 阶段 2 —— 复现 + 最小化

跑循环。看着它变红——bug 出现了。

确认：

- [ ] 循环产生的是**用户**描述的失败模式——不是恰好发生在附近的另一种失败。修错 bug = 白修。
- [ ] 跨多次运行可复现（非确定性 bug 则要求达到足够高的可调试复现率）。
- [ ] 你捕获了确切症状（错误消息、错误输出、缓慢耗时），让后面的阶段能验证修复真的对症。

### 最小化

一旦变红，把复现缩到**仍会变红的最小场景**。砍输入、调用方、配置、数据和步骤，**一次砍一个**，每次砍完重跑循环——只保留对失败来说承重的东西。

为什么要费这个劲：最小复现缩小了阶段 3 的假设空间（留下的可疑活动件更少），并成为阶段 5 干净的回归测试。

当**剩下的每个元素都承重**时完成——去掉其中任何一个，循环就变绿。

在完成复现**并且**最小化之前，不要继续。

## 阶段 3 —— 假设

在检验任何假设之前，先生成**3–5 个排好序的假设**。只生成一个假设会锚定在第一个看似合理的想法上。

每个假设必须是**可证伪的**：说出它所做出的预测。

> 格式："如果 <X> 是原因，那么 <改变 Y> 会让 bug 消失 / <改变 Z> 会让它更糟。"

如果你说不出预测，这个假设就是感觉——丢弃它或锐化它。

**检验前把排序清单给用户看。** 他们常有能瞬间重排的领域知识（"我们刚给 3 号部署了一个改动"），或者知道哪些假设他们已经排除过。廉价的检查点，大量的时间节省。不要卡在这上面——用户不在就按你的排序继续。

## 阶段 4 —— 插桩

每个探针必须对应阶段 3 的一个具体预测。**一次只改一个变量。**

工具偏好：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定向日志**，打在能区分假设的边界上。
3. 永远不要"全量打日志然后 grep"。

**给每条调试日志打唯一前缀标签**，例如 `[DEBUG-a4f2]`。收尾清理就是一次 grep。无标签的日志会活下来；带标签的日志会死掉。

**性能分支。** 性能回归时，日志通常是错的选择。改为：先建立基线测量（计时测试台、`performance.now()`、分析器、查询计划），然后二分。先测量，后修复。

## 阶段 5 —— 修复 + 回归测试

**先写回归测试，再修复**——但只有存在**正确的接缝**时才写。

正确的接缝是指：测试能在调用点复现**真正的 bug 模式**。如果唯一可用的接缝太浅（bug 需要多个调用方才能触发，却只有单调用方测试；单元测试复现不了触发 bug 的那条链），在那里写回归测试会给你虚假的信心。

**如果没有正确的接缝存在，那本身就是发现。** 记下来。代码库架构正在阻止这个 bug 被锁死。把这个发现标记给下一阶段。

如果存在正确的接缝：

1. 把最小化后的复现变成那个接缝处的一个失败测试。
2. 看着它失败。
3. 应用修复。
4. 看着它通过。
5. 用原始的（未最小化的）场景重跑阶段 1 的反馈循环。

## 阶段 6 —— 清理

宣布完成前必须做到：

- [ ] 原始复现不再出现（重跑阶段 1 循环）
- [ ] 回归测试通过（或接缝缺失已被记录）
- [ ] 所有 `[DEBUG-...]` 插桩已移除（`grep` 前缀找）
- [ ] 丢弃式原型已删除（或移到明确标记的调试位置）
- [ ] 被证明正确的假设写进提交 / PR 消息——让下一位调试者学到东西
