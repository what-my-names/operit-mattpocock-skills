# To Tickets

把一份计划、规范或对话拆成一组**票**——曳光弹式垂直切片，每张票都声明**阻塞**它的票。

问题跟踪器和分诊标签词汇应该已经提供给你。如果没有，告诉用户先运行 `setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

从对话上下文里已有的东西出发。如果用户传了一个引用（规范路径、issue 编号或 URL）作为参数，抓取它并读完整的正文和评论。

### 2. 探索代码库（可选）

如果还没探索过代码库，先探索以理解代码当前状态。票的标题和描述应使用项目的领域术语表词汇，并尊重你所接触区域的 ADR。

寻找**预重构**的机会，让实现更轻松。"先让改动变简单，再做那个简单的改动。"

### 3. 起草垂直切片

把工作拆成**曳光弹**票。

<vertical-slice-rules>

- 每个切片切出一条窄但**完整**的通路，穿过每一层（schema、API、UI、测试）——是垂直的，不是某一层的水平切片
- 一个完成的切片可以单独演示或验证
- 每个切片的大小要装得进一个全新上下文窗口
- 任何预重构都应该最先做

</vertical-slice-rules>

给每张票标出它的**阻塞边**——必须先完成才能开始的那些票。没有阻塞项的票可以立即开始。

**宽幅重构是垂直切片的例外。** **宽幅重构**是一种机械改动——重命名一列、改一个共享符号的类型——它的**爆炸半径**横跨整个代码库，一次编辑会同时打破成千上万个调用点，任何垂直切片都无法独自落在绿色上。别把它硬塞进曳光弹；按**扩展–收缩**排序。先扩展：在旧形式旁边加上新形式，什么都不破坏。然后把调用点按爆炸半径分批迁移（按包、按目录），每批是各自的一张票、被"扩展"票阻塞，因为旧形式还在，每批之间 CI 保持绿色。最后收缩：等没有任何调用方了，删掉旧形式，这张票被所有迁移批量票阻塞。当连批都无法单独保持绿色时，保持这个顺序，但让它们共享一个集成分支，所有批都阻塞在最后一张"集成并验证"票上——只有在那里才承诺绿色。

### 4. 拷问用户

把提议的拆解呈现为编号列表。每张票展示：

- **标题**：简短的描述性名称
- **被谁阻塞**：哪些其他票（如果有）必须先完成
- **它交付什么**：这张票让什么端到端行为跑起来

问用户：

- 粒度合适吗？（太粗 / 太细）
- 阻塞边对吗——每张票是否只依赖真正卡住它的票？
- 有该合并或进一步拆分的票吗？

迭代直到用户批准拆解。

### 5. 把票发布到配置好的跟踪器

发布已批准的票。**怎么做**取决于 `setup-matt-pocock-skills` 配置的跟踪器——票本身都一样，只有阻塞边的形态不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下每票写一个文件，从 `01` 按依赖顺序编号（阻塞者在前）。每个文件的"Blocked by"列出它依赖的编号/标题。使用下面的每票文件模板——票一个文件，绝不用一个合并的大文件。
- **真正的跟踪器（GitHub、Linear、……）** → 按依赖顺序（阻塞者在前）每票发一个 issue，这样每张票的阻塞边能引用真实标识符。平台有原生阻塞/子 issue 关系的就用；否则把每张票的"Blocked by"设为阻塞它的 issue。除非另有指示，打上 `ready-for-agent` 分诊标签——这些票天生就是 Agent 可领取的。

推**前沿**：阻塞项全部完成的票。对纯线性链条来说就是从顶到底。

**不要**关闭或修改任何父 issue。
