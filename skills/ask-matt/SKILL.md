## ⚠️ 副作用与边界（市场审核披露）

- **文件**：不直接写文件；被推荐的技能可能读写仓库文件
- **网络**：可能访问帮助来源链接
- **命令**：不直接执行命令
- **凭据/敏感数据**：不直接接触
- **人工确认**：所有高影响操作均由用户确认后执行。


# 询问 Matt

你记不住每个技能，所以要问。

**流程**是穿过各个技能的路径。大多数路径沿一条**主流程**运行，并有两条**入口匝道**并入其中。其他一切都是独立的，或者是在下面运行的词汇层。

## 主流程：想法 → 交付

大多数工作走的路线。你有一个想法，并希望它被实现。

1. **`grill-with-docs`** — 通过采访来加深想法。只要你在**工作目录中工作**，就从这里开始：它是有状态的，把学到的东西留在 `CONTEXT.md` 和 ADR 中。（没有工作目录？用 `grill-me` — 见"独立技能"。两者都运行同一个 `grilling` 原语；`grill-with-docs` 是留下文字记录的那个，所以只要有仓库用来存放记录，它就是两者中更好的选择。）
2. **分支 — 你能在对话里解决每个问题吗？** 如果某个问题需要一个可运行的答案（状态、业务逻辑、你必须亲眼看过的 UI），绕道做一个原型，两个方向都由 **`handoff`** 桥接（原型住在自己的目录里，这正是 `handoff` 的用途——见"阶段边界"）：
   - **`handoff`** 交接出去，然后针对那个文件开一个新会话，
   - **`prototype`** 用一次性代码回答问题，
   - **`handoff`** 把学到的东西带回来，并从最初的想法线程引用它。
3. **分支 — 这是多次会话才能完成的构建吗？**
   - **是** → **`to-spec`**（把线程变成规范），然后 **`to-tickets`** 把它拆成曳光弹票，每张都声明自己的**阻塞边**。在本地跟踪器上，就是 `.scratch/<feature>/issues/` 下每票一个文件，手工按"阻塞者优先"推进；在真正的跟踪器上，边会变成原生阻塞链接，凡阻塞项已完成的票都可以领取——每张票启动 **`implement`**，每张票之间 **`clear`** 上下文。每张票自包含，所以上一张票的上下文是一次性的。
   - **否** → **`implement`** 就在这里，在同一个上下文窗口里。

   无论哪种方式，**`implement`** 都在内部驱动 **`tdd`** 来构建每个问题——每次一个红-绿切片——然后提交前运行 **`code-review`**（对 diff 的双轴审查：标准轴 + 规格轴）收尾。当你只想在没有完整规范的情况下、以测试优先的方式构建一个具体行为时，单独用 **`tdd`**；当你想针对某个固定点审查分支或 PR 时，单独用 **`code-review`**。

### 上下文卫生

把第 1–3 步放在**一个不被打断的上下文窗口**里——在 `to-tickets` 之前不要压缩也不要清空——这样审讯、规范和票都建立在同一套思考上。之后每次 `implement` 重新开始，从票出发。

限制是**[智能区域](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏锐推理的窗口（最先进模型上约 150k token）。如果会话在 `to-tickets` 之前就逼近它，不要勉强降级运行——在最近的阶段边界处 `compact` 然后继续（见"阶段边界"）。

## 入口匝道

产生工作的起始情况，然后并入主流程。

- **Bug 和请求越堆越多** → **`triage`**。它让 issue 走过分诊角色，产出"Agent 就绪"的 issue，之后由 **`implement`** 接走。

  分诊只用于**不是你创建的** issue——bug 报告、到来的功能请求、任何原始素材。`to-tickets` 产出的票已经是 Agent 就绪，所以**不要对它们分诊**。

- **有东西坏了** → **`diagnosing-bugs`**。针对难题：一眼看不透的 bug、间歇性抖动、在两个已知良好状态之间悄悄溜进来的回归。没有**紧反馈循环**之前它拒绝臆测——先找到一条*对这个* bug 已经变红的命令——然后用回归测试修复。当真正的发现是"没有好的接缝把这个 bug 锁死"时，它的复盘交给 **`improve-codebase-architecture`**。

- **一项巨大、雾蒙蒙的工作——绿地项目或超大功能构建，一次会话装不下** → **`wayfinder`**，这里认知要求最高的流程。当从这里到目的地的路还不可见时，它在问题跟踪器上绘制一张**决策票**的**共享地图**，一次解决一张——产出**决策，而不是交付物**——直到迷雾被推开、道路清晰。**`grill-with-docs`** 打磨的是你能在一次会话里握得住的想法，wayfinder 针对的是你握不住的——而且它更慢更密，所以只留给这种场景，绝不用在一个范围明确的功能上。

  地图清晰后，**它交接，不负责构建**：在 **`to-spec`** 处并入主流程，把地图上链接的决策折叠成可构建的计划，然后照常走 `to-tickets` 和 `implement`。把地图直接甩进 `implement` 会跳过折叠、丢掉链接细节——只有当工作确实很小的时候才直接进 `implement`。

## 代码库健康

不是功能工作——是维护。

- **`improve-codebase-architecture`** — 有空就跑，保持代码库适合 Agent 在其中工作。它浮出**深化机会**；挑一个，它*生成一个想法*，你可以在 `grill-with-docs` 处带进主流程。它是找到候选者的普查；**`codebase-design`**（下方）是你设计所选候选的工作台。

## 下面的词汇

两个模型调用的参考，运行在其他技能的*下方*——各自是其词汇的唯一事实来源。当问题出在**用词**而不是流程时，直接找它们；或者让上面的技能把它们拉进来。

- **`domain-modeling`** — 打磨项目的*领域*语言：挑战模糊术语，解决一词多职（"account"干三种活），把难以逆转的决定记录为 ADR。它是 `grill-with-docs` 驱动的主动纪律，让 `CONTEXT.md` 保持一份干净的术语表。
- **`codebase-design`** — 用于设计模块*形状*的深模块词汇（module、interface、depth、seam、adapter、leverage、locality）：干净接缝处的小接口后面藏着大量行为。`tdd` 和 `improve-codebase-architecture` 都说这种语言。

## 阶段边界

**阶段**是会话内部的一块工作——审讯、实现、QA。在两者之间的**边界**处，你有五个选择，而在其中做选择是整张地图里最模糊的决定：

- **继续** — 留在原地。不花成本，也没有损失。
- **`clear`** — 清空窗口，当这里没有任何东西与接下来的事有关时。
- **`handoff`** — 写一份可移植的 Markdown 文件。用途很窄：只用于**新工具**、**新目录**、**同事**，或者阶段**中途**分叉一个副任务。它买来的是可移植性。
- **子代理** — 把范围严格的任务送到它自己的窗口，拿回一份报告。
- **`compact`** — 压缩当前上下文，用它播种一个新会话。**默认选项**，位于决策树的底部而不是首选。

读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 看有序决策树——那五个问题、每条分支背后的推理，以及为什么一手来源的成本让**继续**成为首先要排除的选项。在边界**处**做决定；阶段中途则继续，或者把剩下的拆给子代理。

## 独立技能

完全脱离主流程。

- **`grill-me`** — 和 `grill-with-docs` 一样的不懈采访，但**无状态**：它不在本地保存任何东西，也不构建 `CONTEXT.md`。当你**不在工作目录中工作**时用它——打磨一份计划、一个设计、一篇文字，任何下面没有仓库的东西。如果你在工作目录里，改用 `grill-with-docs`：它运行同样的采访并留下文字记录，严格优于前者。
- **`grilling`** — 采访原语本身：轮次、前沿、事实是 Agent 的活、决定是你的。`grill-me` 和 `grill-with-docs` 是两条有名字的入口，`triage`、`wayfinder` 和 `improve-codebase-architecture` 都在内部运行它。只有当你想要不带任何包装的采访本身时，才直接用它。
- **`resolving-merge-conflicts`** — 逐 hunk 处理进行中的合并或变基冲突，按**意图**解决——意图追溯到每一方的一手来源，而不是挑行——然后完成操作。它从不运行 `--abort`。独立于所有流程：当你已经身处冲突之中时用它。
- **`prototype`** — 一个小的、一次性的程序，回答一个设计问题：这个状态模型感觉对吗，或者这个 UI 应该长什么样。一次性是对代码写法的约束，不是销毁它的承诺：答案折叠进真实代码，原型本身作为**一手来源**保留在主分支之外的 `prototype/<name>` 分支上，由实现 issue 指向它。它是主流程第 2 步的绕道，但任何时候设计问题在纸面上难以敲定，都可以用它。
- **`research`** — 把阅读的跑腿活委托给**后台 Agent**：它用**一手来源**调查问题，然后在仓库里留下一份带引用的 Markdown 文件。它读的时候你继续干活。它产出的文件是带*进*主流程（`grill-with-docs` 处）的素材——research 喂给思考，但不取代思考。
- **`to-questionnaire`** — 当挡路的东西不在你的脑子里、也不在代码库里，而是在**别人的**脑子里时，这个技能给对方写一份要填的问卷。它是 `grill-me` 的反面：不是就主题采访你，而是就**送达方式**采访你——发给谁、你需要拿回什么——然后把问题瞄准缺口。回来的东西是 `grill-with-docs` 或 `to-spec` 的素材。
- **`wizard`** — 用于只有**人类**能走的步骤：配置基础设施、设置凭据或 CI 机密、点过不熟悉的第三方控制台、跑一次一次性迁移或切换。它生成一个交互式 bash 脚本，打开每个 URL、捕获每个值、写进 `.env` 和 GitHub secrets——于是这个流程不再是你每次都要向 Agent 重新解释的东西。模型调用，所以 Agent 一撞上只有你能通过的墙就会伸手用它。如果 Agent 自己能做，它就该自己做；这是给人类真正在环的场景。
- **`wait-what`** — 对没送达的消息的纠偏。对话中途、在任何其他技能内部使用它，Agent 会用你缺的那块上下文、用大白话、用 `CONTEXT.md` 的词汇，把它刚说的话重新讲一遍。它事后生效；`grill-with-docs` 是事前解药，因为早早约定的共同语言能让行话压根不出现。
- **`teach`** — 用多次会话学一个概念，把当前目录当有状态的工作区。
- **`writing-for-agents`** — 写给 Agent 看的文档的参考：技能、AGENTS.md、有明确指向的文档。
