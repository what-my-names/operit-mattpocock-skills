# 测试驱动开发

TDD 是红→绿的循环。这项技能是让这个循环产出"值得保留的测试"的参考手册：什么是好测试、测试放在哪里、有哪些反模式、循环的规则是什么。每一节在**每个循环**都适用——在循环前和循环中查阅，而不是事后。

在探索代码库时，请阅读 `CONTEXT.md`（如果存在），让测试名称和接口用词与项目的领域语言保持一致，并尊重你所接触区域的 ADR。

## 什么是好测试

测试通过公共接口验证行为，而不是验证实现细节。代码可以彻底重写；测试不该变。一个好测试读起来就像一份规格说明——"用户可以用有效购物车结账"这句话精确告诉你存在什么能力——并且能扛住重构，因为它不关心内部结构。

示例见 [tests.md](tests.md)；模拟（mock）指南见 [mocking.md](mocking.md)。

## 接缝——测试该放在哪

**接缝**是你测试所依托的公共边界：你在不触及内部的情况下观察行为的那个接口。测试写在接缝处，永远不针对内部结构。

**只在预先约定的接缝处测试。** 写任何测试之前，先写下要测试的接缝并与用户确认。未经确认的接缝处不得编写测试。你不可能什么都测——预先约定接缝，正是让测试精力落在关键路径和复杂逻辑上、而不是铺满每个边界情况的办法。

问："公共接口是什么？我们应该测试哪些接缝？"

当接口本身的形态存疑——模块该有多深、接缝该放在哪、接口该暴露什么——请用技能名 "codebase-design" 调用 Skill 工具获取词汇表。它是 module、interface、depth、seam、adapter、leverage、locality 这些术语的统一来源，是查阅用的参考资料，而不是要运行的一次会话。

## 反模式

- **与实现耦合** — mock 内部协作者、测试私有方法，或者通过旁路验证（查数据库而不是走接口）。特征：一重构测试就挂，尽管行为没变。
- **同义反复** — 断言按代码的算法重新算了一遍期望值（`expect(add(a, b)).toBe(a + b)`、用同样方式手推出来的快照、断言常量等于它自己），于是测试必然通过、永远不可能和代码意见相左。期望值必须来自独立的事实来源——已知正确的字面量、手算过的例子、规格说明。
- **水平切片** — 先把所有测试写完，再写全部实现。批量测试验证的是*想象中*的行为：你测的是事物的形状而不是面向用户的行为，测试对真实变化变得不敏感，而且你在理解实现之前就锁死了测试结构。相反，要用**垂直切片**：一个测试 → 一个实现 → 重复；每个测试都是一颗**曳光弹**，回应上一轮循环教给你的东西。

## 循环的规则

- **先红后绿。** 先写失败的测试，然后只写刚好能让它通过的代码。不要预判未来的测试，也不添加投机性的功能。
- **一次一个切片。** 每个循环只做一条接缝、一个测试、一个最小实现。
- **重构不属于这个循环。** 重构属于评审阶段（见 `code-review` 技能），而不是红→绿的实现循环。
