# 代码库设计

设计**深层模块**：大量行为藏在小接口后面，放在干净的接缝处，可通过该接口测试。无论在哪里设计或重构代码，都使用这套语言和原则。目标是让调用者获得杠杆，让维护者获得局部性，让所有人都获得可测试性。

## 术语表

严格使用这些术语——不要用"component"、"service"、"API"或"boundary"来代替。一致的语言才是重点。

**模块（Module）**——任何有接口和实现的东西。刻意与规模无关：一个函数、类、包，或横跨多层的切片。_避免_：unit、component、service。

**接口（Interface）**——调用者为了正确使用模块所必须知道的一切：类型签名，还有不变量、顺序约束、错误模式、必需配置和性能特征。_避免_：API、signature（太窄——它们只指类型层面的表面）。

**实现（Implementation）**——模块内部的东西，它的代码主体。与 **Adapter** 区分：一个东西可以是小适配器配大实现（Postgres 仓库），也可以是大适配器配小实现（内存假实现）。当话题是接缝时用"adapter"；其他情况用"implementation"。

**深度（Depth）**——接口处的杠杆：调用者（或测试）每学习一个单位接口，能驱动多少行为。当一个模块的小接口后面藏着大量行为时，它是**深**的；当接口几乎和实现一样复杂时，它是**浅**的。

**接缝（Seam）** _（Michael Feathers）_——一个你可以不修改原处就能改变行为的地方；模块接口所在的*位置*。把接缝放在哪里本身就是一个设计决定，与接缝后面放什么无关。_避免_：boundary（被 DDD 的有界上下文污染了含义）。

**适配器（Adapter）**——在接缝处满足接口的具体东西。描述的是*角色*（它填补哪个槽位），不是实质（它里面是什么）。

**杠杆（Leverage）**——调用者从深度中获得的东西：每学习一个单位接口，获得更多能力。一份实现回报 N 个调用点和 M 个测试。

**局部性（Locality）**——维护者从深度中获得的东西：变更、bug、知识和验证集中在一处，而不是扩散到所有调用者。修一次，处处修好。

## 深与浅

**深模块** = 小接口 + 大量实现：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少，参数简单
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 复杂逻辑藏在里面
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 少量实现（要避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多，参数复杂
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是把活转手
└─────────────────────────────────┘
```

设计接口时问自己：

- 能减少方法数量吗？
- 能简化参数吗？
- 能把更多复杂性藏进里面吗？

## 原则

- **深度是接口的属性，不是实现的属性。** 一个深模块内部可以是由小的、可模拟的、可替换的部分组成的——它们只是不属于接口。一个模块可以同时有**内部接缝**（实现私有，供自己的测试用）和接口处的**外部接缝**。
- **删除测试。** 想象删掉这个模块。如果复杂性消失了，它就是个转发器。如果复杂性重新出现在 N 个调用者身上，它就在赚它的位置。
- **接口就是测试面。** 调用者和测试跨过同一个接缝。如果你需要*越过*接口去测试，这个模块的形状可能有问题。
- **一个适配器意味着假设的接缝。两个适配器才意味着真实的接缝。** 除非有东西真的跨接缝变化，否则不要引入接缝。

## 为可测试性设计

好接口让测试变得自然：

1. **接受依赖，不要自己创建。**

   ```typescript
   // 可测试
   function processOrder(order, paymentGateway) {}

   // 难测试
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **返回结果，不要制造副作用。**

   ```typescript
   // 可测试
   function calculateDiscount(cart): Discount {}

   // 难测试
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **表面面积小。** 方法越少 = 需要的测试越少。参数越少 = 测试搭起来越简单。

## 关系

- 一个**模块**恰好有一个**接口**（它呈现给调用者和测试的表面）。
- **深度**是**模块**的属性，以它的**接口**来衡量。
- **接缝**是**模块**的**接口**所在的位置。
- 一个**适配器**坐在**接缝**处，满足**接口**。
- **深度**为调用者产出**杠杆**，为维护者产出**局部性**。

## 被否定的表述

- **深度 = 实现行数 / 接口行数**（Ousterhout）：奖赏了灌水的实现。我们用深度即杠杆。
- **"Interface" 当作 TypeScript 的 `interface` 关键字或类的公共方法集**：太窄——这里的接口包括调用者必须知道的每个事实。
- **"Boundary"**：被 DDD 的有界上下文占用了。说 **seam** 或 **interface**。
