## ⚠️ 副作用与边界（市场审核披露）

- **文件**：创建一次性原型文件（丢弃性质）
- **网络**：可能安装依赖包
- **命令**：运行原型相关命令
- **凭据/敏感数据**：不接触凭据或敏感数据
- **人工确认**：所有高影响操作均由用户确认后执行。


# 原型

原型是**回答一个问题的丢弃式代码**。问题决定形状。

## 选一条分支

先确定正在回答的是哪个问题——从用户的提示、周边代码，或者用户在的话就问一句：

- **"这个逻辑 / 状态模型感觉对吗？"** → [LOGIC.md](LOGIC.md)。构建一个可分享的独立 HTML 文件——自由点击的按钮加上分页的引导式走查——把状态机推过那些在纸面上很难推理的用例，而且非开发者也能上手操作。
- **"这应该长什么样？"** → [UI.md](UI.md)。在一条路由上生成几个截然不同的 UI 变体，通过 URL 查询参数和一个底部悬浮条切换。

两条分支产出的东西完全不同——选错会浪费整个原型。如果问题确实模棱两可、又联系不上用户，就默认选择与周边代码更匹配的分支（后端模块 → 逻辑；页面或组件 → UI），并在原型顶部注明这个假设。

## 两条分支都适用的规则

1. **从第一天起就是丢弃的，并且明确标记。** 把原型代码放在它最终会被用到的地方旁边（挨着它要原型化的模块或页面），这样上下文一目了然——但命名要让随便一个读者都看得出这是原型，不是生产代码。对于丢弃式 UI 路由，遵循项目已有的路由惯例；不要发明新的顶层结构。
2. **跑起来零门槛。** UI 原型用项目任务运行器里的一条命令启动——`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击就开的单个 HTML 文件。无论哪种，启动都不需要动脑子。
3. **默认不持久化。** 状态存在内存里。持久化是原型要*检验*的东西，不是它该依赖的东西。如果问题明确涉及数据库，用一个临时库或一个本地文件，名字写清楚"PROTOTYPE — 用完可删"。
4. **跳过打磨。** 不写测试，错误处理只做到让原型*能跑*，不建抽象。目标是尽快学到东西。
5. **把状态亮出来。** 每次操作后（逻辑分支）或每次切换变体时（UI 分支），打印或渲染完整的相关状态，让用户看见什么变了。
6. **完成时把它留下来。** 把通过验证的决定折叠进真实代码，然后把原型本身留作**一手来源**：提交到丢弃分支、不进主分支，并在实现 issue 上留一个指向该分支的上下文指针。把答案也记下来——结论和它敲定的那个问题——记在 issue 或提交里。主分支只保留那个通过验证的决定。
